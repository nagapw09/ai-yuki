# Проверки 0.3.2 — 18 сентября 2026

Это протокол замеров, а не обещание готовности. Всё, что не проверено вживую,
отмечено отдельно.

## 1. Распознавание речи без ключей

Ни одного ключа провайдера в базе нет: единственный включённый провайдер —
`claude_cli` (подписка, у неё нет эндпоинта транскрипции). Поэтому `voice_start`
раньше вообще не запускался, и «позвал → слушает» было невозможно физически.

### Что пробовали до принятого решения

| Путь | Итог |
|---|---|
| `whisper-rs` в процессе | Не собирается. `whisper.cpp` компилируется, но `whisper-rs-sys 0.13.1` выдаёт вырожденные биндинги: `size_of::<whisper_full_params>()` = 1, `error[E0080]`. С `LIBCLANG_PATH` — то же самое. |
| Встроенное распознавание Windows | Ни одного распознавателя в системе: `HKLM\SOFTWARE\Microsoft\Speech_OneCore\Recognizers\Tokens` и `…\Speech\Recognizers\Tokens` пусты, `Get-WinUserLanguageList` не показывает речевых пакетов. |
| Официальная сборка `whisper.cpp` рядом | Работает. Выбрано. |

### Проверено на живом движке

`whisper-bin-x64.zip` v1.9.2, 7,8 МБ, содержит `whisper-server.exe` + `whisper.dll`
+ ядра `ggml-cpu-*.dll`. Эндпоинт — `/inference`, **не** `/v1/audio/transcriptions`:
последний отвечает `File Not Found`. Именно поэтому в `yuki-voice` добавлена
`transcription_endpoint`.

Тестовые фразы синтезированы голосом Windows «Microsoft Irina Desktop», 16 кГц моно.

| Фраза | base (141 МБ) | small (488 МБ) |
|---|---|---|
| «Юки, открой браузер» | «Юки, открой браузер.» | «Юки, открой браузер.» |
| «Юки, какая сегодня погода» | «Юки, какая сегодня погода?» | «Юки, какая сегодня погода?» |
| «Юки, напомни мне позвонить маме в семь вечера» | «…маме **всем** вечера.» ✗ | «…маме в 7 вечера.» ✓ |
| Задержка на фразу 2,8–4,6 с | 0,90–0,91 с | 2,56–2,67 с |

`ggml-small-q5_1` (190 МБ) проверен и отвергнут: 3,8–5,0 с, то есть медленнее
неквантованной `small`. Замеры грубые — три сервера делили ядра.

Отдельно проверено, что движок принимает запрос ровно той формы, которую шлёт
`HttpStt` (поля `model`, `file` с именем `speech.wav`, `language`): ответ
`{"text":" Юки, открой браузер.\n"}`.

По умолчанию выбрана `small`: правильно понятая команда важнее двух секунд.

### Чего эта проверка НЕ покрывает

- Живой микрофон пользователя не проверялся. Речь синтезирована, а не произнесена.
- VAD на реальном фоне комнаты не проверялся: порог начала и конца фразы может
  потребовать подстройки.
- Слово «Юки» в потоке живой речи не проверялось. Акустические образцы не записаны,
  поэтому работает текстовый путь: распознаётся всё, что VAD принял за речь, и
  обращение ищется в тексте уже локально.
- Whisper на шуме и тишине склонен выдумывать фразы. Неадресованные отбрасываются,
  но после одиночного «Юки» окно в восемь секунд может поймать выдумку.

## 2. Счётчики компьютера

Пользователь сообщил, что панель не сходится с диспетчером задач. Замерено на той
же машине:

| Величина | Что показывала Yuki | Что показывает диспетчер задач |
|---|---|---|
| CPU | 16,6 % (`% Processor Time`, расчёт sysinfo) | **49,7 %** (`% Processor Utility`) |
| Память | 16,1 / 31,7 ГБ, 51 % | 16,3 / 31,7 ГБ, 52 % |
| C: | 62 %, 358,8 ГБ свободно | 62 %, 358,8 ГБ свободно |
| D: | 69 % | 69 % |

Расхождение было только в CPU: `% Processor Time` не учитывает частоту процессора
и на турбо занижает загрузку втрое. Теперь читается тот же счётчик, что у
диспетчера задач.

GPU показывал 61,2 % — число верное, но в системе **две** видеокарты:

```
luid_0x00000000_0x0000fc59  engtype_3d   61,2 %
luid_0x00000001_0x1b7e7e8b  engtype_3d   25,5 %
```

Диспетчер задач показывает их раздельно, Yuki показывала максимум без имени —
сравнивать было не с чем. Теперь каждый адаптер идёт со своим названием из DXGI
(`Intel(R) Iris(R) Xe Graphics`, `NVIDIA GeForce RTX 4060 Laptop GPU`).

## 3. Погода по параметрам Windows

`Geolocator::DefaultGeoposition` на этой машине не задан, поэтому карточка
показывала ошибку. Регион в параметрах Windows задан всегда:

```
HKCU\Control Panel\International\Geo → Name = RU, Nation = 203
Get-WinHomeLocation → GeoId 203, Россия
```

Добавлен запасной путь: город → точка Windows → страна из параметров → её столица.
Геокодер сам отдаёт локализованное имя, поэтому «Moscow» в запросе превращается в
«Москва, Россия» в карточке (проверено: `Moscow → Москва | Россия 55.75204 37.61781`,
`Kyiv → Киев | Украина`, `Berlin → Берлин | Германия`).

1. **Движок переживал аварийное завершение Yuki.** При обычном закрытии он

   жёсткого убийства приложения движка в списке процессов нет.
2. **Распаковка складывала в папку пользователя 22 посторонних исполняемых
   файла** — `bench.exe`, `whisper-talk-llama.exe`, тесты. Берутся только
   `whisper-server.exe` и библиотеки. Папка `speech` — 475 МБ вместо 485 МБ.

## 7. Главный экран по раскладке Astra и разбор счётчика CPU

### CPU: счётчик возвращён на `% Processor Utility`

Я дважды менял этот счётчик, и первый раз отменил правильное решение по одному
случайному сравнению. Окончательно, с доказательством:

```
базовая частота i5-12500H : 2500 МГц, турбо до 3760
Processor Time            : 12 / 14 / 13 / 13 %
Processor Utility         : 22 / 21 / 19 / 26 %
```

Отношение устойчиво около 1,6 — ровно отношение частот. На снимке пользователя
диспетчер задач показывал 26 % при 16 % у Yuki на `Time`: то же отношение 1,63.
Значит диспетчер считает `Utility`.

Проверено после возврата, четыре выборки подряд:

```
Yuki CPU          : 26 / 24 / 33 / 26 %
Processor Utility : 26 / 29 / 32 / 25 %
```

**Урок на будущее:** загрузка скачет на десятки процентов между соседними
секундами (в одном ряду встречались 12, 13, 13, 46). Сравнивать два окна по
одному мгновению бессмысленно — только несколько выборок подряд.

### Что грузит встроенную видеокарту

Пользователь спросил, почему Iris Xe держится на 99–100 % при выключенной
3D-модели. Замер по процессам:

```
chrome        44,0 %
wallpaper64   35,4 %   (Wallpaper Engine, живые обои)
dwm           20,5 %   (композитор рабочего стола)
итого         100 %
```

Вклад Yuki — ноль: её окна рисуются на дискретной RTX 4060. Ни 3D-модель, ни
убранный шар к этой видеокарте отношения не имели.

### Раскладка

Главный экран переписан по композиции Astra: слева погода и курс, в центре имя,
состояние и две кнопки, справа показатели, под центром — что играет, в нижнем
углу — быстрые значки. Навигация переехала из боковой рейки наверх строкой.
Убраны шар, строка ввода и список дисков.

Обе видеокарты показываются отдельными строками.

### Плеер: что играет

Новые команды `media_now_playing` и `media_control` читают медиасессию Windows и
передают нажатия работающему плееру. Своего звука Yuki не проигрывает.

Диагностика нашла две вещи:

1. Карточка пряталась, если плеер не сообщил названия. Сессия без метаданных —
   это всё равно «что-то играет»; теперь подпись берётся из имени источника.
2. WinRT-вызовы шли в потоке `spawn_blocking`, где COM не инициализирован.
   Добавлен `CoIncrementMTAUsage` один раз на процесс. Изолировать этот эффект
   отдельно не удалось — правка оставлена как заведомо верная, а не как
   подтверждённая причина.

Проверено на настоящей медиасессии Windows (беззвучный источник):
`available: true`, `playing: true`, позиция идёт, карточка отрисовалась с
прогрессом и кнопкой паузы. С живым плеером название и исполнитель приходят от
него; на этой машине проверить не удалось — ни один плеер не запустился.

Для будущей диагностики оставлен `apps/desktop/src-tauri/tests/media_probe.rs`
(помечен `#[ignore]`, в обычный прогон не попадает).

### Кнопки плеера и бегущее время

Пользователь сообщил: название подхватилось из браузера верно, но кнопки не
работают, а время стоит на месте. Нашлись две отдельные причины.

**Кнопки.** Чтение сессии имело запасной путь, а команды — нет:

```
строка 507 (чтение)  : GetCurrentSession().or_else(… GetSessions …)
строка 560 (кнопки)  : GetCurrentSession()?          ← без запасного пути
```

Когда Windows не назначает «текущую» сессию — обычное дело для фоновой вкладки
браузера, — карточка отрисовывалась, а кнопки молча не делали ничего. Выбор
сессии вынесен в общую функцию `current_session`.

**Время.** `GetTimelineProperties().Position` — это снимок на момент
`LastUpdatedTime`, а не бегущие часы. Браузер обновляет его редко, поэтому
строка стояла всю песню. Добавлен досчёт прошедшего времени, ограниченный
длительностью дорожки.

Проверено на медиасессии Windows:

```
позиция сразу      : 8,2 с
позиция через 4 с  : 12,2 с   (сдвиг ровно 4,0)
кнопки             : пауза=да, далее=нет, назад=нет
media_control      : команда принята, playing true → false
```

Дополнительно: кнопки, которые плеер не объявляет рабочими, теперь показываются
выключенными, а не мёртвыми, и ошибка команды выводится под карточкой вместо
молчания.

Название и исполнитель из настоящего браузера подтвердил пользователь; на этой
машине синтетический источник метаданных не отдаёт.

### Пауза, отзывчивость и погода по часовому поясу

**Пауза не срабатывала.** Стоял `TryTogglePlayPauseAsync` — переключатель, который
решает направление сам, по своему представлению о состоянии. Когда оно
расходилось с нашим, нажатие «пауза» запускало воспроизведение заново. Теперь
статус читается прямо в момент нажатия и вызывается явная `TryPauseAsync` или
`TryPlayAsync`.

Проверено: `playing` true → false, позиция замерла на 23,5 и не убегает;
обратное нажатие вернуло true.

**Затупы при переключении.** Карточка опрашивала плеер раз в две секунды, и
новое название появлялось с задержкой до двух секунд. Добавлены повторные
чтения после команды (120, 400, 900, 1600, 2600 мс) — браузер меняет метаданные
не мгновенно, одного запроса через четверть секунды не хватало.

Время теперь идёт само между опросами: локальный счётчик добавляет полсекунды
каждые полсекунды, а опрос лишь сверяется с плеером. Это и плавнее, и дешевле,
чем опрашивать WinRT каждую секунду.

**Погода по часовому поясу.** По просьбе пользователя регион заменён на часовой
пояс. Имя IANA сразу содержит город: `Europe/Moscow` → Moscow. Windows хранит
свои названия вроде `Russian Standard Time`, поэтому пояс берётся из `Intl`
в интерфейсе, а не из Win32.

Разница оказалась существенной: регион в параметрах Windows — `RU`, а часовой
пояс — `Europe/Warsaw`. Погода теперь показывает **Варшаву**, а не Москву.

Порядок определения: заданный город → точная точка Windows → часовой пояс →
столица страны. Последний шаг остался на случай служебных поясов (`UTC`,
`Etc/GMT+3`), в которых города нет.

### Дёрганье времени и «пауза не останавливает»

Догадки заменены измерением на настоящей сессии Chrome (поднята в отдельном
профиле, пользовательский не трогался). Chrome сообщает позицию **один раз** и
больше её не обновляет:

```
Position | с последнего обновления | сумма
    0.03 |                   69.42 | 69.45   ← отчёт в начале дорожки
   69.47 |                    1.79 | 71.26
   69.47 |                    3.29 | 72.76
```

То есть досчёт по `LastUpdatedTime` верный и монотонный, а дёрганье добавлял
интерфейс. Он складывал «ответ плеера + свой счётчик» и обнулял счётчик на
каждом ответе. Ответ приходит с задержкой, поэтому на каждом опросе показания
прыгали назад на доли секунды.

Теперь время идёт от опоры: запомненная позиция плюс прошедшее с момента
сверки. Опора переставляется только при смене дорожки, на паузе или при
расхождении больше полутора секунд — мелкая разница ответа игнорируется.

Проверено 30 замерами за 18 секунд:

```
128 129 129 130 131 131 132 132 133 133 134 135 135 136 …  145
шагов назад: 0
```

**Пауза.** На уровне Windows она работала: `TryPauseAsync` возвращал `Ok(true)`,
статус менялся на Paused, и нажатие кнопки через интерфейс тоже срабатывало.
Ошибка была в другом: направление выбиралось по состоянию, а состояние на
экране могло разойтись с настоящим. Тогда нажатие «пауза» уходило как «играть».

Теперь интерфейс шлёт явное намерение — `pause` или `play` — то самое, которое
нарисовано на кнопке, и Rust его не переигрывает. Просьба о паузе у уже
остановленного плеера просто ничего не делает. Состояние на кнопке меняется
сразу после нажатия, не дожидаясь ответа.

Проверено через настоящий клик по кнопке: «Играть» → `playing: true`, повторное
нажатие → `playing: false`, время на паузе стоит.

Что Chrome сообщает о своих возможностях: `пауза=True, play=False, далее=False,
назад=False` — у одиночной дорожки кнопок переключения нет, и они показываются
выключенными.

## 9. Почему голос выдавал бессмыслицу

Пользователь сказал, что программа не похожа на завершённый продукт. Вместо
очередных вопросов я прошёл приложение сам и нашёл в **его собственной истории
чата** доказательство: его голосовые реплики приходили как «Роденной», «Логов
таблила», «Ммм». Это не опечатки — это выдумки распознавания.

### Измерение, а не догадка

Диагностика микрофона (`cargo run -p yuki-voice --example mic_check`) в тишине:

```
уровень шума:      0.064     ← очень высокий
пиковая громкость: 0.129
порог начала:      0.120     ← упёрся в постоянный потолок, НИЖЕ пиков шума
порог остановки:   0.070     ← НИЖЕ самого фона
кадров с речью:    227 из 252  в тишине
```

Порог остановки 0,070 лежал ниже фона 0,064–0,129, поэтому начавшаяся «фраза»
не заканчивалась никогда. Микрофон непрерывно отдавал шум распознаванию, и оно
непрерывно сочиняло текст. Отсюда и мусор в чате, и восемь процентов процессора.

Замер уровня в работающем приложении подтвердил: **931 кадр из 931 громкие**,
уровень прижат к единице постоянно.

### Три исправления

1. **Потолок порога зависит от фона.** Постоянные 0,12 и 0,07 рассчитаны на
   тихий вход. Теперь потолок не ниже `фон × 2,4`, с жёсткой границей 0,22,
   чтобы шумная комната не сделала Yuki глухой. На тихом микрофоне ничего не
   меняется: там постоянный потолок и так выше.

2. **Начало речи требует 60 мс подряд выше порога.** Всплеск фона длится
   кадр-другой, речь — десятки.

3. **Упреждающий буфер 300 мс.** Детектор объявляет речь на кадре, который уже
   громче порога, а начало слова нарастает тише. Без буфера распознавание
   получало фразу без первого звука.

### Фильтр выдумок по языку

Полного разделения у громкого микрофона нет: пики шума и тихая речь
перекрываются. Поэтому вторая линия — в самом распознавании.

Проверено на настоящих ответах `whisper.cpp`:

| | речь | чистый шум |
|---|---|---|
| текст | «Юки, открой браузер» | «Возьмите и не забывайте» |
| определённый язык | russian 0,985 | nynorsk 0,571 |
| **вероятность русского** | **0,985** | **0,022** |
| `no_speech_prob` | 0,820 | 0,000016 |

`no_speech_prob` бесполезен — на чистом шуме он утверждает, что это точно речь.
А оценка языка честная. Короткие команды проверены отдельно: «Юки» — 0,723,
«Юки, стоп» — 0,567, «открой браузер» — 0,974. Порог 0,25 разделяет с запасом в
обе стороны.

### Результат

| | было | стало |
|---|---|---|
| громких кадров в тишине | 931 из 931 | 30 из 2095 |
| ложных распознаваний за 47 с тишины | постоянно | **0** |
| речь обычной громкости | тонула в мусоре | «Юки, открой браузер» → `открой браузер`, `addressed: true` |

### Что осталось

Проверял речью через динамики. На тихой громкости фраза до детектора не
доходила, на обычной — распозналась верно. **Живой голос пользователя остаётся
решающей проверкой**: динамики звучат тише человека у микрофона.

Корень всё равно в усилении микрофона: фон 0,055–0,076 при пиках до 0,27 — это
много. Снижение уровня микрофона или отключение «Microphone Boost» в параметрах
Windows улучшит и распознавание, и расход процессора.

## 10. Эхо, чужой разговор и подавление шума

Пользователь прислал снимок: Yuki взяла одно слово из его разговора с другим
человеком, ответила, **услышала собственный ответ и ответила себе**.

### Эхо: проверка стояла не в том месте

Заслон был такой:

```rust
if wake_word && speaking_now(&worker) { continue; }
```

Он спрашивал «говорит ли синтезатор **сейчас**» в момент, когда запись уже
дошла до очереди распознавания. К этому времени Yuki успевала замолчать, и её
собственная речь проходила насквозь.

Теперь признак ставится **при захвате**: любой кадр фразы, пришедшийся на
собственную речь, помечает её целиком (`Utterance::self_voice`). Флаг держится
всё время озвучивания плюс 700 мс на эхо комнаты.

### «Открой браузер» всё-таки работал

Проверено напрямую: «открой блокнот» через чат → инструмент «Открыть
приложение» → `готово · 88 мс` → блокнот действительно запущен (PID
подтверждён процессом). В истории пользователя нашлось и «открой браузер» →
«Переключиться на окно» → Chrome на переднем плане за 128 мс.

Chrome был уже запущен, поэтому внешне выглядело как «ничего не произошло».
Агент исправен; до него не доходил правильный текст.

### Подавление шума — корневое исправление

Из проекта [Priler/jarvis](https://github.com/Priler/jarvis), на который указал
пользователь, взят `nnnoiseless` — порт RNNoise. Он встроен в захват **до**
пересчёта частоты: сеть обучена на 48 кГц, а микрофон отдаёт именно их.

Измерено той же диагностикой, в тишине, три прогона:

| | до | после |
|---|---|---|
| уровень шума | 0,042…0,076 | **0,000** |
| пиковая громкость | 0,129…0,27 | **0,004…0,011** |
| кадров «с речью» из 252 | 227 | **0** |
| порог начала | 0,120 (потолок) | 0,020 (минимум) |

Пороги упали до минимальных — значит теперь слышна и тихая речь, которая
раньше тонула в фоне.

**Речь при этом не страдает.** Один и тот же файл до и после обработки:

```
до подавления:    «Юки, открой блокнот.»   ru=0,989
после подавления: «Юки, открой блокнот.»   ru=0,989
```

### Что ещё стоит взять у jarvis

- `rustpotter` — специальный детектор слова пробуждения вместо «распознавать всё
  подряд и искать имя в тексте». Снимет и расход процессора, и срабатывания на
  чужой разговор.
- `vosk` — быстрое офлайн-распознавание коротких команд.
- `seqdiff` — нечёткое сравнение команд, терпит ошибки распознавания.

### Граница проверки

Проверял речью через динамики ноутбука. Такой тракт добавляет эхо комнаты и
окраску динамика: распознавание по нему ошибается там, где на чистом файле не
ошибается вовсе. **Живой голос у микрофона остаётся решающей проверкой.**
